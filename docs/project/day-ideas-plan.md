## 1. Конечная цель

> **На https://nemczzz-rgb.github.io/Weekend_Search/ человек за 3 нажатия от главной находит, чем заняться дома, в городе или сочетая оба варианта, и получает готовый сценарий из 2–3 связанных занятий. Он открывает понятный пошаговый план (для пиццы — рецепт с честным предупреждением о 48–72 часах в холодильнике и подборкой фильмов по жанру), добавляет сценарий в свой день и сам редактирует день, в котором места города и домашние занятия стоят рядом. Сайт построен на новом дизайне, выведенном из описанного UX. Все факты взяты из проверенной базы знаний с источниками. Сайт работает на телефоне и компьютере и обновляется сам после каждого merge в `main`.**

Цель достигнута, когда выполнены все критерии приёмки из раздела 3 и прогон TASK-052 подтверждён обоими участниками. Кроме того, демо должно быть готово к переезду на собственный сервер без переписывания экранов (раздел 12).

### Что не входит

- Помощник с ИИ на сайте, аккаунты, серверная база, Python/FastAPI. Это TASK-004–013, они по-прежнему ждут TASK-003.
- Покупка билетов, бронирование, оплата, ссылки на онлайн-кинотеатры и указание, где смотреть фильм.
- Встроенная карта и расчёт маршрута. Для мест с адресом остаются только внешние ссылки «Открыть на карте».
- Автоматический сбор событий по расписанию: события обновляются вручную (D6).
- Другие языки, кроме русского. Аналитика и счётчики.

### Связь с документами проекта

ТЗ v0.1 ([technical-specification.md](technical-specification.md)) описывает будущий продукт с помощником и сервером. Эта фича, как TASK-014–028, — отдельное поручение пользователей по статическому интерфейсу. Она не закрывает TASK-003 и не начинает TASK-004–013. Формулировка ТЗ владелицы «Сохрани утверждённый дизайн» заменяется решением D1 и действует только после его утверждения владелицей.

## 2. Исходное ТЗ владелицы (пересказ по пунктам)

1. Отдельная вкладка «Идеи для дня» рядом с местами и планом: дома, в городе или вместе.
2. Результат — сценарий из 2–3 связанных занятий, а не список идей. Примеры: римская пицца и фильм; фигурка из глины и книга; парк с кофе, затем домашний спа-вечер.
3. Карточка коротко показывает: для кого (одному, вдвоём, с друзьями), сколько времени, что понадобится, можно ли сегодня. По нажатию открывается подробный план с шагами. На карточке нет полного рецепта.
4. Первая подробная идея — «Римская пицца под киновечер» по рецепту владелицы: точные ингредиенты и количества, автолиз, замес, брожение, формирование, двухэтапная выпечка, советы, начинки, подача. Рецепт разбит на раскрывающиеся блоки. До выбора идеи видно, что тесто выдерживается в холодильнике 48–72 часа. Идея не предлагается как выполнимая сегодня с нуля.
5. После рецепта — выбор жанра и небольшая подборка из списка владелицы. Жанры: романтика, комедия, драма, триллер, фантастика, фэнтези, семейное кино, мультфильмы, приключения, уютное кино. Названия видны без регистрации и сервисов. Наличие на платформах не придумывать.
6. Пожелания учитывают домашние занятия: «музей, а вечером дома фильм», «парк и спа-вечер» дают план с местами и занятием. «Только дома» — план без маршрута и карты. Пользователь сам добавляет, убирает и переставляет занятия.
7. Путь: вкладка → выбор идеи → подробный план → добавление в свой день. Адаптивность и работа существующих кнопок сохраняются. Никаких вымышленных адресов, цен, расписаний и ссылок.

## 3. Критерии приёмки

| ID | Критерий | Как проверяется |
| --- | --- | --- |
| AC-DI-01 | От главной до подробного плана идеи не больше 2 нажатий, до добавления в день не больше 3 | Ручной прогон 390 и 1280 px |
| AC-DI-02 | В «Идеях для дня» есть фильтры «Дома / В городе / Вместе», «Для кого» и «Сколько времени»; сброс одним действием | Ручной прогон + тест фильтрации |
| AC-DI-03 | Карточка показывает для кого, время, что понадобится, статус «сегодня»; полного рецепта на карточке нет | Сверка с UX-спецификацией |
| AC-DI-04 | У пиццы предупреждение «тесто 48–72 ч в холодильнике» видно на карточке и в начале плана, до кнопки «В мой день». Статус никогда не «Можно сегодня» | Тест `canStartToday` + прогон |
| AC-DI-05 | Рецепт пиццы содержит все блоки из п. 4 ТЗ. Ингредиенты и количества совпадают с текстом владелицы | Тест сравнения с `docs/knowledge-base/owner/pizza-recipe.md` + вычитка владелицей |
| AC-DI-06 | 10 жанров, в каждом в базе не меньше 15 фильмов. На экране сначала до 6, остальные по кнопке «Показать ещё». Фильмы из списка владелицы стоят первыми. Названия видны без входа, ссылок на платформы и постеров нет | Валидатор базы знаний + прогон |
| AC-DI-07 | Шесть эталонных пожеланий из раздела 8.3 дают ожидаемый черновик | Автотест `planner` |
| AC-DI-08 | В домашнем дне нет адресов, ссылок на карту и отметок перемещений | Тест + прогон |
| AC-DI-09 | Добавить, убрать, переставить и перенести в другой день можно для мест, занятий и своих пунктов, в том числе с клавиатуры | Автотест хранилища плана + прогон с клавиатуры |
| AC-DI-10 | План сохраняется после перезагрузки; «Очистить план» с подтверждением или отменой | Прогон |
| AC-DI-11 | Нет фактов без источника, CI-валидатор зелёный. Прошедшие события скрыты автоматически | CI + тест с подменой даты |
| AC-DI-12 | 360–1440 px без горизонтальной прокрутки; контраст WCAG 2.2 AA; виден фокус; `prefers-reduced-motion` учитывается | Прогон + проверка контраста по токенам |
| AC-DI-13 | Каждая функция из инвентаря аудита (TASK-037) работает либо убрана с обоснованием в UX-спецификации | Чек-лист регрессии |
| AC-DI-14 | JS+CSS первого экрана ≤ 150 КБ gzip; изображение ≤ 300 КБ; картинки ниже первого экрана грузятся лениво. Коллекции базы знаний подгружаются при открытии своего экрана (`import()`), а не в общем бандле | Отчёт сборки |
| AC-DI-16 | К выпуску база знаний не меньше объёмов D14, валидатор зелёный | Валидатор выводит счётчики |
| AC-DI-17 | Код готов к переезду: правила P1–P8 раздела 12 соблюдены | Автотест `portability` в CI + ревью PR |
| AC-DI-18 | План можно сохранить в файл и загрузить в другом браузере без потерь | Автотест + прогон |
| AC-DI-19 | Та же сборка без `PAGES_BASE` работает с корня обычного статического сервера; инструкция переезда есть | Прогон TASK-057 |
| AC-DI-15 | Выпуск в `main`, CI и `deploy` зелёные, сайт открывается по адресу Pages | Actions + браузер |

## 8. Логика плана (контракт для TASK-047)

### 8.1. Модель

```ts
type PlanItem =
  | { kind: 'place'; uid: string; placeId: string }
  | { kind: 'event'; uid: string; eventId: string }
  | { kind: 'activity'; uid: string; activityId: string; ideaId?: string; filmGenre?: GenreId; filmId?: string }
  | { kind: 'custom'; uid: string; title: string; address?: string }

type PlanDay = { date: string /* YYYY-MM-DD */; items: PlanItem[] }
type Plan = { version: 1; days: PlanDay[] /* 1 или 2 */ }
```

- `uid` — уникален внутри плана, один и тот же объект можно добавить только один раз. Повторное добавление показывает, где объект уже стоит, как сейчас (TASK-020).
- Добавление сценария кладёт его занятия подряд в выбранный день в порядке сценария.
- Удаление с отменой в течение 5 секунд.
- Не больше 6 пунктов в день; при попытке добавить седьмой — сообщение, без добавления.

### 8.2. Разбор пожелания (без ИИ)

Текст переводится в нижний регистр, «ё» заменяется на «е». Совпадения ищутся по началу слова, как в текущем `planner.ts`. Ниже начальный словарь; расширяет его только TASK-047, и каждое слово покрывается тестом.

| Сигнал | Слова |
| --- | --- |
| `home` | дома, домой, домашн, на диване, вечером дома |
| `film-home` | фильм, кино дома, киновечер, сериал + сигнал `home` |
| `cinema` | кино, кинотеатр — **без** сигнала `home` |
| `cooking` | готов, пицц, испечь, рецепт |
| `selfcare` | спа, ванн, маск, отдохнуть дома |
| `craft` | глин, лепить, рисова, творч |
| `reading` | книг, почитать, читать |
| городские | существующие синонимы `planner.ts`: прогулка, история, искусство, парк, еда, вода, архитектура, дизайн, тихо |

Правила:
1. Только домашние сигналы → домашний день: 2–3 занятия, без мест и событий.
2. Городские и домашние вместе → сначала места (как сейчас, до 4), домашнее занятие последним («вечер»).
3. `cinema` → место-кинотеатр из каталога; `film-home` → занятие «Киновечер».
4. Нет сигналов → поведение как сейчас.

### 8.3. Эталонные пожелания (автотест)

| Пожелание | Ожидаемый черновик |
| --- | --- |
| «музей, а вечером дома фильм» | 1–3 места с тегом «искусство», затем занятие «Киновечер» последним |
| «парк и спа-вечер» | 1–3 места с тегом «парк», затем занятие «Домашний спа-вечер» последним |
| «хочу весь день дома» | Только занятия (2–3), ни одного места, адреса и ссылки на карту |
| «пицца и кино» | Сценарий «Римская пицца под киновечер», предупреждение о начале теста (8.4) |
| «сходить в кино» | Место-кинотеатр, домашнего фильма нет |
| «прогулка по старому центру» | Тот же результат, что до изменений (регрессия) |

### 8.4. Статус «сегодня»

Для сценария считаются `lead = max(leadTimeHours.min)` и `active = сумма durationMinutes` занятий.
- `lead > 0` → статус «Начать за N дней» (N = ⌈lead/24⌉…⌈max/24⌉, для пиццы «за 2–3 дня»). Никогда не «Можно сегодня».
- Иначе, если от текущего локального времени до 23:00 больше `active` → «Можно сегодня».
- Иначе → «Лучше в другой день».

Часы работы мест здесь не учитываются, потому что данные о них неполные. При добавлении сценария с `lead > 0` в день с датой D план показывает: «Поставьте тесто не позже <D − ⌈lead/24⌉ дней>».

## 9. Схема базы знаний (контракт для TASK-035 и линии Б)

Общие правила для всех коллекций:
- `id` — латиница, kebab-case, уникален в коллекции;
- текст на русском;
- любой факт (адрес, часы, цена, дата события, год фильма) — с `source` (https-URL или `"owner"`) и `checkedAt` (`YYYY-MM-DD`);
- неизвестное поле **отсутствует**, а не заполняется догадкой.

| Коллекция | Обязательные поля | Необязательные | Правила валидатора |
| --- | --- | --- | --- |
| `places.json` | id, title, kind, area, durationMinutes, note, tags[] | address, hours, price, source, checkedAt, mapQuery | hours/price/address только вместе с source и checkedAt |
| `events.json` | id, title, dateStart, source, checkedAt | dateEnd, time, placeId, address, price | dateEnd ≥ dateStart; placeId существует; прошедшие не удаляются, их скрывает UI |
| `films.json` | id, title, year, genres[] (из 10 id), origin: owner/research | originalTitle, note (≤ 100 символов), source, checkedAt | для `research` обязательны source и checkedAt; счётчик по жанрам; нет полей url/platform/poster; нет дублей по title+year |

## 12. Готовность к переезду на свой сервер

Демо живёт на GitHub Pages. Следующий шаг после демо — свой сервер: сначала та же статика на своём домене, затем, возможно, API с базой и аккаунтами (TASK-004–013). Правила ниже обязательны в спринте 3: тогда переезд меняет несколько файлов, а не все экраны.

| ID | Правило | Зачем |
| --- | --- | --- |
| P1 | Экраны и компоненты получают данные базы знаний **только** через `content/load.ts`. Интерфейс асинхронный (`Promise`), даже когда данные лежат в бандле: `getCollection(name)`, `getById(name, id)`. Импортировать `*.json` из `src/content` можно только в `content/static-source.ts` | При переходе на API пишется `ApiContentSource` на `fetch`, экраны не меняются |
| P2 | План читается и сохраняется **только** через `plan/store.ts` поверх интерфейса `PlanRepository { load(): Promise<Plan>; save(plan: Plan): Promise<void> }`. Обращаться к `localStorage` можно только в `plan/repository-local.ts` | Сервер с аккаунтами — новая реализация `ApiPlanRepository` |
| P3 | Никаких адресов `github.io` и путей `/Weekend_Search/` в коде. Пути к файлам — через `import.meta.env.BASE_URL`, адрес сайта задаётся только переменной CI | Смена домена — одна переменная |
| P4 | `content/types.ts` — это будущий контракт API. Поле не удаляется и не переименовывается без миграции; `id` стабильны, потому что на них ссылаются сохранённые планы и будущие таблицы | Данные переносятся в SQLite один к одному |
| P5 | `Plan` хранится с полем `version`; при изменении формата пишется миграция из прежней версии в `plan/migrate.ts` | Старые планы не ломаются ни в браузере, ни на сервере |
| P6 | Сборка не зависит от хостинга: задача `web` собирает `dist`, задача `deploy` только публикует. Хостинговые настройки — только в `deploy` | Замена Pages на `rsync`/Docker — одна задача CI |
| P7 | Состояние навигации в адресе — только через query-параметры (`?view=plan&idea=roman-pizza`), без путей `/plan/...` | Работает на Pages и любом статическом сервере без настройки «все пути → index.html» |
| P8 | Автотест `tests/web/portability.test.mjs` в CI проверяет P1–P3: нет импорта `content/*.json` вне `static-source.ts`, нет `localStorage` вне `repository-local.ts`, нет `github.io` и `/Weekend_Search/` в `src/` | Правила не размываются со временем |

Что остаётся сделать при переезде, когда демо закончится:
1. **Статика на своём домене** — по `docs/deployment/self-hosting.md` (TASK-057): сервер, домен, задача `deploy`, переадресация со старого адреса, экспорт и импорт планов пользователями.
2. **API и база** — отдельный проект (TASK-004–013, после TASK-003). Включает `ApiContentSource`, `ApiPlanRepository`, загрузку JSON базы знаний в SQLite по схеме раздела 9. Экраны при этом не переписываются.
