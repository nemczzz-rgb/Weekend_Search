## Пересмотр 2026-11-09

Пользователь подтвердил, что ключа ещё нет. Повторный живой запрос к KudaGo из текущей среды вернул HTTP 403. Причина отказа по-прежнему неизвестна. В отличие от отсутствующего ключа, ограничение Яндекса подтверждено [официальными условиями](https://yandex.ru/dev/commercial/doc/ru/): бесплатная версия предназначена только для сайтов или приложений, к которым может обратиться любой пользователь сети Интернет. Локальный сайт в домашней сети этому условию не соответствует. Получать бесплатный ключ для текущей архитектуры не требуется.

Пользователь выбрал локальный выпуск и 0 ₽; [ADR-003](../decisions/ADR-003-local-map-reassessment.md) согласовывает направление OpenStreetMap с локальным расчётом. Конкретный движок остаётся кандидатом до завершения проверки. TASK-003 заблокирована; основная разработка не начата.

### Живой пробный прогон OpenStreetMap и московского транспорта

- Подложка Leaflet/OpenStreetMap открыта на компьютере через `/osm/`: 24 тайла загрузились, ошибок 0; увеличение масштаба и переключение линий проверены визуально. [Правила тайлов OSM](https://operations.osmfoundation.org/policies/tiles/) требуют атрибуцию, обычную загрузку видимой области и соблюдение ограничений; офлайн-скачивание не выполнялось.
- Взяты шесть [официальных московских наборов](https://data.mos.ru/opendata/60661) GTFS наземного транспорта 60661–60666. Выгрузка содержит 17 850 остановок, 962 маршрута, 211 298 рейсов и 10 790 612 записей времени остановок. В наборе маршрутов: 925 автобусных, 36 трамвайных, 1 канатный; метро нет. Из-за несовпадающих версий 5 296 848 записей времени ссылаются на отсутствующие в выгрузке рейсы. [Портал](https://data.mos.ru/developers) указывает CC BY 4.0 с атрибуцией; перед выпуском нужно проверить точные условия каждого набора.
- Для 2026-11-14 собран временный GTFS с 824 маршрутами, 81 369 рейсами и 2 130 600 записей времени после фильтрации ссылок. Использованы московский [OSM PBF](https://data.bbbike.org/osm/bbbike/Moscow/Moscow.osm.pbf), [OpenTripPlanner 2.10.0](https://docs.opentripplanner.org/en/latest/Basic-Tutorial/) и переносимая Java 25. На компьютере с около 8 ГБ ОЗУ граф построен за 5 мин 18 с и сохранён в 218 МБ; сервер загружен. При сборке отмечены 6048 изолированных остановок и 7269 остановок без связей для пересадок — покрытие требует оценки.
- Запрос от района Театральной до Парка Горького на 2026-11-14 12:00 вернул отдельно пеший путь 3489 м / 46 мин 40 с и автобус м90 с пешими участками 4240 м / около 38 мин. Оба показаны на диагностической карте; для автобуса источник не содержит `shapes.txt`, поэтому его синий пунктир лишь соединяет остановки и не является точной траекторией. Не считать это готовым решением для всех видов транспорта.
- Ключи и платные сервисы не использованы; все большие выгрузки, Java и граф находятся в игнорируемой `.local/`. Это компьютерная проверка одного маршрута, не тест физического телефона и не подтверждение качества всех расписаний.

## Что реализовано для проверки

- Консольные прогоны KudaGo, статуса Codex и изолированного App Server без зависимостей приложения.
- Страница карты с отдельными реальными pedestrian/masstransit-запросами, визуальным подтверждением подложки и ручным подтверждением физического телефона.
- В отчёт карты входят только разрешённые статусы. Ключ, геометрия, расстояние, длительность и исходные ответы не сохраняются.
- Локальный сервер обслуживает только диагностические файлы и отчёты в памяти; доступ к файлам репозитория не предоставляется.
- Начальная страница просмотрена в браузере: все проверки ожидают запуска, запись/скачивание отчёта отключены. Успешный результат без ключа не выставлен.
- HTTP readiness: health, HTML, JS и CSS возвращают 200; путь к AGENTS.md вне списка диагностических файлов возвращает 404.

Пройдены 18 проверок самих инструментов на стандартном unittest и Node syntax check. Итоговая проверка: 80 локальных ссылок в 30 Markdown-файлах, нерабочих ссылок нет. Эти проверки не заменяют живые интеграции, pytest/Vitest/Playwright будущего приложения и физический телефон. Диагностический сервер после проверки остановлен; для продолжения его нужно запустить по инструкции.

## Выявленные особенности и исправления

1. Вход CLI внутри ограниченного процесса и в обычном контексте пользователя отличается. Первоначальное Not logged in не означало отсутствия действующего входа владельца.
2. Пустая таблица mcp_servers объединяется с пользовательской конфигурацией. Перед запуском модели унаследованные записи требуется явно отключить в дочернем процессе и проверить config/read; личный config.toml не изменяется.
3. Установленный протокол не поддерживает пример readOnly/access из открытой документации в том же виде. Сгенерированы публичные схемы CLI в игнорируемую .local/protocol; применён поддерживаемый именованный профиль permissions. Ограничения не ослаблялись.
4. На Windows дочерний процесс закрывается до удаления его временной рабочей папки.

Прогон ограничений — конкретная проверка конфигурации и границы на установленной версии, не универсальный аудит всех будущих версий. В TASK-008 ограничения необходимо сохранить и перепроверить.
