# Правила работы агентов

Этот файл применяется ко всему проекту и предназначен для всех агентов, людей и аккаунтов, работающих с репозиторием. Если инструмент не читает `AGENTS.md` автоматически, его нужно открыть вручную.

## Начало сессии

1. Прочитать `CONTEXT.md`, `memory/CURRENT.md` и `memory/TASKS.md`.
2. Проверить фактические файлы и локальные изменения. Если Git настроен, выполнить `git status --short`; не считать память точнее текущего кода.
3. Прочитать документы и согласованные решения, относящиеся к задаче. При продолжении чужой работы прочитать соответствующий файл в `memory/handoffs/`.
4. Обозначить задачу в `memory/TASKS.md`: ID, исполнитель, статус и область изменений. До начала параллельной работы согласовать пересечения с другими исполнителями.

## Границы работы

- Выполнять текущий запрос пользователя. Последние явные инструкции пользователя имеют приоритет над документами проекта; ограничения среды и безопасности обязательны.
- Пользователь утвердил ТЗ и поручил реализацию по docs/project/implementation-plan.md; выбранный стек и границы описаны в docs/project/technical-specification.md.
- До полного успеха TASK-003 не начинать TASK-004 и основную реализацию. Отсутствие входа, ключа или прогона на физическом телефоне не считать успешной проверкой. Скрипты проверки и документация разрешены до контрольной точки.
- Бюджет — 0 рублей дополнительных платежей. Бесплатные ключи разрешены; платные API, автосписания и временный платный пробный период как основа демо исключены.
- Стек: React/TypeScript/Vite, Python/FastAPI/Pydantic 2, SQLite. Выпуск локальный и в домашней сети; не заменять Python облачным бэкендом и не публиковать проект без отдельной задачи.
- Не превращать предположения в требования. Неопределённость помечать явно; предложения отделять от согласованных решений.
- Обычные обратимые действия внутри поставленной задачи выполнять самостоятельно. Существенные продуктовые и архитектурные решения выносить на согласование с пользователем.
- Не удалять и не перезаписывать чужие изменения, не выполнять разрушительные операции Git и не публиковать проект без соответствующего поручения.
- Не добавлять в проект токены, пароли, персональные данные, реальные `.env` или приватную переписку. Примеры конфигурации должны содержать только безопасные заглушки.

## Несколько агентов и аккаунтов

- Для каждой задачи использовать уникальный ID вида `TASK-001` и понятное имя исполнителя, например `account-a/agent-ui`. Не указывать личные данные и секреты.
- Один файл в каждый момент меняет один исполнитель. При пересечении задач сначала распределить файлы или последовательность работы.
- `TASKS.md` — договорённость, а не автоматическая блокировка. Между независимыми копиями проекта нужен общий актуальный источник файлов и явная координация.
- После настройки Git для параллельной разработки предпочтительны отдельные ветки или worktree на задачу. Не переключать общую рабочую копию, пока ей пользуется другой агент.
- Общие файлы памяти редактировать последовательно. Перед сохранением перечитать актуальный файл и сохранить записи других исполнителей. Конфликты разрешать по смыслу, сохраняя обе выполненные работы.
- Не полагаться на историю чата, внутреннюю память модели или доступность аккаунта предыдущего исполнителя. Существенные факты фиксировать в проекте.
- Наличие этих правил не является поручением запускать дополнительные агенты. Их запуск определяется текущей задачей пользователя и возможностями среды.
- Помощник на сайте отделён от агентов разработки. Он не получает историю разработки, репозиторий, shell и личные коннекторы; ограничения проверяются в TASK-003.

## Качество и завершение

- Писать документацию на русском; имена каталогов, файлов и идентификаторы — понятные и последовательные. Кодовые соглашения будут определены после выбора стека.
- Делать изменения соразмерными задаче. Не добавлять зависимости, абстракции и документацию без практической необходимости.
- Проверять результат подходящим способом: для документации — ссылки, структуру и согласованность; для будущего кода — применимые проверки проекта. Не заявлять об успешных проверках, которые не запускались.
- До передачи работы обновить статус задачи, `memory/CURRENT.md`, если состояние изменилось, и добавить краткую запись в `memory/LOG.md`.
- Для незавершённой работы создать передачу по `memory/handoffs/TEMPLATE.md`. В ней указывать факты, следующие действия и блокеры, а не полную переписку.
- В ответе пользователю кратко сообщить результат, способ проверки и существенные ограничения.

## Источники истины

- `CONTEXT.md` — назначение проекта, подтверждённые ограничения и принципы.
- `memory/CURRENT.md` — актуальный этап, открытые вопросы и ближайшее продолжение.
- `memory/TASKS.md` — задачи, исполнители и статус.
- `docs/decisions/` — причины и статус существенных решений.
- `memory/LOG.md` — история завершённых действий; старые записи не описывают текущий статус.
- Код и фактическая конфигурация — реальное поведение системы. При расхождении с документами нужно проверить причину и исправить источник ошибки.
